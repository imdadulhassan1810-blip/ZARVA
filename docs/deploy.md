# Put ZARVA online

This guide takes the code from your computer to a real website, for example `https://zarva.in` (website) and `https://api.zarva.in` (API). You don't need to install anything new; everything happens in a browser.

**Cost (approximate, Nov 2026, check the sites):** Render starter plans are about $7 per month each for the API and website, and a small PostgreSQL about $6 per month, so roughly ₹1,700 per month. A `.in` domain is about ₹700 per year. Render's free plans sleep after 15 minutes of no visitors (the first visitor then waits about a minute) and its free database is deleted after 30 days, so use them only to try things out.

## What you need first

| Thing | Why | Where | Ready? |
|---|---|---|---|
| GitHub account with this repository | Render deploys from it | github.com | ✓ |
| Render account | Runs the API, website and database | https://render.com (sign in with GitHub) | |
| A domain name | Your web address | GoDaddy, Hostinger, Namecheap, Cloudflare | |
| MSG91 account + **DLT approval** | Sign-in OTP and booking SMS | msg91.com + your operator's DLT portal (Jio/Airtel/Vi) | pending |
| Razorpay account + **KYC** | Taking payments | dashboard.razorpay.com | pending |
| Resend account | Sign-in codes by email | resend.com (free tier is enough) | |

**Important:** on a real server the API refuses to start without these keys, on purpose (so it can never run with fake sign-in or fake payments). You can still go online before DLT and KYC are approved:
- **Razorpay:** use the **test mode** keys (they start with `rzp_test_`, available right after sign-up, no KYC). Payments are pretend until you swap in live keys.
- **MSG91:** your auth key is available right after sign-up; create the OTP template in MSG91 and use its template id. SMS will not reach phones until DLT approves the template, so meanwhile sign in with **email** (works as soon as Resend is set up).

## What works before the approvals come through

Be clear about this before you tell anyone the site is live:

| Until this is approved | What real people can't do |
|---|---|
| **DLT** (SMS) | No SMS reaches anyone. Partners sign in **only** with an SMS code, so no partner can sign in. Customers can sign in by email, but booking needs a verified mobile number (sent by SMS), so **no customer can book**. Booking updates by SMS are off too. |
| **WhatsApp (Meta)** | No WhatsApp updates. Everything else works. |
| **Razorpay KYC** | With `rzp_test_` keys, online payment would be **pretend money**, so the live site hides "Pay online" and customers can only choose **Pay after service**. It comes back by itself the moment you put in live keys (`rzp_live_...`). For a private test site only, `ALLOW_TEST_PAYMENTS=true` shows it anyway. |

So: you can put the site online now to check that it runs, but real bookings in Durgapur start the day DLT is approved.

## Step 1. Create everything on Render (about 15 minutes)

1. Sign in at https://render.com with your GitHub account and allow it to see the **ZARVA** repository.
2. Click **New → Blueprint**, choose the ZARVA repository, branch `main`. Render reads `render.yaml` and shows three things to create: `zarva-db` (database), `zarva-api` and `zarva-web`.
3. Render asks for the values marked "sync: false". Fill in what you have now; you can change any of them later under the service → **Environment**:
   - `PUBLIC_WEB_URL` and `CORS_ORIGINS`: your website address, e.g. `https://zarva.in` (both are required; the API won't start without `CORS_ORIGINS`, because the website could not talk to it). If you don't have a domain yet, use the address Render gives `zarva-web` (like `https://zarva-web.onrender.com`).
   - `NEXT_PUBLIC_API_URL` (on zarva-web): the API address, e.g. `https://api.zarva.in` or `https://zarva-api.onrender.com`.
   - MSG91, Resend and Razorpay keys are required (see above). Google keys are optional: leave `GOOGLE_CLIENT_ID` empty and the Google button is simply hidden.
4. Click **Apply**. The first build takes about 5 to 10 minutes. `JWT_SECRET` and `KYC_ENCRYPTION_KEY` are generated by Render automatically. **Never change `KYC_ENCRYPTION_KEY` later**: partner ID documents already uploaded could no longer be opened.
5. When `zarva-api` shows **Live**, open `https://<api address>/health`. You should see `{"ok":true}`. The database tables and the Durgapur catalogue are created automatically on first start.
6. Create your admin account: open **zarva-api → Shell** and run `pnpm admin:create ops "Your Name"`. Add the printed authenticator key to Google Authenticator on your phone, then sign in at `https://<website>/admin/login` and change the password under **Team**. There is no admin sign-up page, on purpose.

If the API fails to start, open **zarva-api → Logs**. The API refuses to start with unsafe settings and says exactly which one, for example "Set PUBLIC_WEB_URL to your website address in production".

### Built-in protection you can tune (zarva-api → Environment)

- **Sign-in code limits.** One internet address can ask for at most `CODE_LIMIT_PER_IP_PER_HOUR` codes an hour (default 20), and the whole site sends at most `SMS_CODE_LIMIT_PER_HOUR` SMS codes an hour (default 500). The second one is a ceiling on your MSG91 bill if someone abuses the sign-in page; when it is hit, people are asked to sign in with email, and the API log says "hourly SMS code limit reached". Raise it as you grow.
- **Website sign-in.** The long-lived sign-in token is kept in a secure cookie by the website's own server (`/session/...`), not in the browser's storage, so a malicious script on a page can't take over accounts. Nothing to set up.

## Step 2. Your own domain (about 30 minutes, plus waiting for DNS)

1. Render → **zarva-web → Settings → Custom Domains → Add** `zarva.in` and `www.zarva.in`. Render shows the DNS records to add.
2. Render → **zarva-api → Settings → Custom Domains → Add** `api.zarva.in`.
3. At your domain seller, add the records Render showed (usually a CNAME for `www` and `api`, and an A record for the bare domain). HTTPS certificates are added automatically once DNS works, usually within an hour.
4. Update the settings to the new addresses: `PUBLIC_WEB_URL` and `CORS_ORIGINS` on zarva-api, `NEXT_PUBLIC_API_URL` on zarva-web. Changing `NEXT_PUBLIC_API_URL` needs a new build: **zarva-web → Manual Deploy → Deploy latest commit**.
5. Add `https://zarva.in` to Google sign-in's **Authorised JavaScript origins** (README, "Google sign-in").

## Step 3. Switch on the real services as they get approved

| When this is approved | Change on zarva-api → Environment |
|---|---|
| DLT for the OTP template | `OTP_PROVIDER=msg91`, `MSG91_AUTH_KEY`, `MSG91_TEMPLATE_ID` (already set by the blueprint, just fill the keys) |
| DLT for the booking-update templates (docs/notifications.md) | `SMS_PROVIDER=msg91`, `MSG91_SMS_TEMPLATES=booking_confirmed:<id>,pro_assigned:<id>,...` |
| WhatsApp templates in Meta | `WHATSAPP_PROVIDER=meta`, `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID` |
| Razorpay KYC | `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`; in Razorpay → Webhooks add `https://api.zarva.in/v1/payments/webhook/razorpay` with `payment.captured` and `payment.failed` |
| RazorpayX (automatic payouts, optional) | `PAYOUT_PROVIDER=razorpayx`, `RAZORPAYX_ACCOUNT_NUMBER`, `RAZORPAYX_WEBHOOK_SECRET`; in RazorpayX → Webhooks add `https://api.zarva.in/v1/m/home/payouts/webhook` with `payout.processed`, `payout.failed`, `payout.reversed` |

Saving an environment change restarts the API by itself (about a minute).

## Phone apps (later)

Store builds of the ZARVA and ZARVA Partner apps need the live API address. Set `API_URL` (e.g. `https://api.zarva.in`, must start with `https://`) in `apps/mobile/eas.json` under each build profile's `env`, or as an EAS environment variable. The build stops with a clear message if it is missing, so the app can never ship pointing at "localhost".

## Every later update

Merge a pull request into `main` on GitHub. Render rebuilds and redeploys both services automatically, and database changes (migrations) run on start. Nothing to do on your side.

## Backups

Render takes daily backups of paid PostgreSQL plans. Before a big change you can also download one: **zarva-db → Backups**.

## Not using Render?

The API is a normal Docker image (`Dockerfile.api` at the repository root) and the website is a standard Next.js app, so Railway, Fly.io, a DigitalOcean droplet or AWS all work. Use any PostgreSQL 16 (Neon, Supabase, RDS) and copy the settings from `render.yaml`. Keep the API in an India or Singapore region so it is fast for Durgapur.
